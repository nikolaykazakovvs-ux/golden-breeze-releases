# Регламент актуализации витрины (`docs/CONTENT-MAINTENANCE.md`)

**Дата утверждения: 28 октября 2026 года.**  
Регламент определяет правила синхронизации публичной витрины Golden Breeze (`README.md`, `docs/index.html`, `docs/roadmap.md`, `docs/first-start.md`) в репозитории `nikolaykazakovvs-ux/golden-breeze-releases`.

---

## 1. Позиционирование и изоляция

- **Концепция продукта:** Golden Breeze — мультиагентная платформа для трейдинга (совместная работа специализированных ИИ-агентов в торговом процессе от анализа рынка и принятия решений до исполнения, сопровождения позиций и контроля риска под управлением пользователя). Исследования и стратегии — прикладной инструмент, а не самостоятельная замена концепции.
- **Изоляция:** репозиторий содержит только материалы витрины и метаданные раздачи. Исходный код ядра, рабочие базы, приватные ключи и секреты сюда не помещаются.

---

## 2. Разделение ответственности и автоматизация

- **Выпускающий агент (Release Agent):** обязан проверить и синхронизировать витрину при выпуске каждого релиза через согласованный PR.
- **Регламентная сверка (Showcase Maintenance):** страхует пропуски, запускается по расписанию и читает только изменившиеся источники.
  - Действует локальная автоматизация «Актуальность витрины Golden Breeze» (ID `golden-breeze-2`, ежедневно 10:00 Europe/Kyiv; её запуск зависит от включённого рабочего места; отдельный release event hook пока не реализован).
  - **Принцип невмешательства:** при отсутствии расхождений коммиты, ветки, PR и запуски CI **не создаются**. Уведомление формируется только при обнаружении расхождения или блокера.
- **Доставка:** изменения вносятся в отдельной ветке и сливаются в `main` через PR после независимого ревью (`reviewer != worker`).

---

## 3. Разделение источников истины

1. **Метаданные релиза:** список GitHub Releases и сопутствующие манифесты (`build-manifest.json`, `first-install.json`, `.sha256`).
2. **Статусы функций:** утверждённая дорожная карта проекта и акты функциональной приёмки. Одной записи в Releases **недостаточно** для обновления статусов готовности функций.

---

## 4. Условия признания выпуска и правила ссылок

- **Критерии валидности для витрины:**
  1. Недрафтовый статус (`isDraft == false`);
  2. Принадлежность к каналу `stable` (*«stable» обозначает имя канала дистрибуции для пользователей, а не гарантию зрелости кода на стадии alpha*);
  3. Наличие автономного установщика `GoldenBreeze-FirstInstall-<version>.exe`;
  4. Согласованность контрольной суммы SHA-256 с манифестом.
- **Экономная проверка:** проверяющий не скачивает 380 МБ установщик каждый день, а переиспользует receipt проверки неизменившихся точных байтов (сверка SHA-256 из манифеста), проверяя бинарный артефакт только при обнаружении нового или изменённого релиза.
- **Запрет `/releases/latest`:** GitHub API отсекает pre-release из эндпоинта latest. Витрина ссылается на конкретный тег (`/releases/tag/vX.Y.Z-alpha`) или общий список `/releases`, сохраняя маркировку `Alpha`.
- **Снятый или отозванный выпуск:** если активный релиз отозван или удалён, витрина не должна оставлять неработающую ссылку: кнопка переключается на предыдущий валидный выпуск канала `stable` либо блокируется с понятным сервисным сообщением.

## 5. Градации статусов и триггеры обновления

- **Градации:**
  - `release-published` — сборка упакована в FirstInstall, выложена в Releases и проверена по SHA-256.
  - `implemented` — код функции реализован в кодовой базе.
  - `tested` — пройдены автоматические или профильные тесты на стенде.
  - `accepted` — завершена живая приёмка сценария на реальном или демо-контуре (MT5/FTMO).
  - `planned` — плановая цель дорожной карты.
- **Доставка != приёмка:** публикация `FirstInstall` подтверждает доставку сборки, но не означает завершения полной приёмки торговых сценариев (особенно на счёте `Real`).
- **Триггеры обновления:** публикация нового валидного релиза канала `stable`; изменение подтверждённой готовности функций; изменение утверждённого плана; изменение требований/установщика; исправление дефектов документации.
- **Бережное обновление (No mass-rewrite):** исторические номера версий в архивах и отчётах не переписываются на новый номер; обновляются только актуальные карточки, ссылки, хеши и срез статусов.

---

## 6. Согласованный комплект обновления витрины и двуязычный паритет

- **Синхронность `RU` и `EN`:** любое обновление публичных данных синхронно затрагивает русские и английские материалы витрины. Не допускается расхождение номеров версий, размеров, хешей `SHA-256`, ссылок на артефакты и статусов готовности между локалями.
- При фиксации изменений согласованным PR синхронно обновляются:
  1. `README.md` (EN) и `README.ru.md` (RU) — витрина репозитория (скачивание, `SHA-256`, срез состояний, ссылки);
  2. `docs/index.html` (RU) и `docs/en/index.html` (EN) — веб-лендинг GitHub Pages (hero, хеш, системный статус в Пульте, матрица направлений);
  3. `docs/roadmap.md` (RU) и `docs/en/roadmap.md` (EN) — детальная карта возможностей и таблица направлений;
  4. `docs/first-start.md` (RU) и `docs/en/first-start.md` (EN) — инструкция по установке, сверке `SHA-256` в PowerShell и автообновлению.
- **Профильная проверка паритета и скрипта:** перед подачей PR выполняются воспроизводимые stdlib-проверки из корня репозитория:
  - `python tools/check_bilingual.py` — сверка фактов релиза (`v0.12.0-alpha`, байтов, `SHA-256`, среза `111 / 84`), паритета карточек `data-status` и `id` между `RU` и `EN`, валидности локальных ссылок и якорей, метаданных `lang`/`hreflang`/`canonical` и отсутствия запрещённых ссылок `/releases/latest`;
  - `node --check docs/app.js` — проверка синтаксиса клиентского скрипта витрины.
