# Контракт раздачи установщика и витрины (`DISTRIBUTION-CONTRACT.md`)

**Актуализация: 12 ноября 2026 года.** Этот документ фиксирует правила публикации выпусков и работы публичной витрины в репозитории `nikolaykazakovvs-ux/golden-breeze-releases`. Наличие опубликованного установщика подтверждает доставку сборки, но не заменяет полную функциональную приёмку торговых и пользовательских сценариев.

## 1. Назначение репозитория и витрины

- **Репозиторий витрины и релизов:** `golden-breeze-releases` предназначен для публичной раздачи проверенных установщиков `FirstInstall`, заметок к выпускам, пользовательских инструкций и веб-лендинга GitHub Pages (из ветки `main`, каталог `/docs`, целевой адрес `https://nikolaykazakovvs-ux.github.io/golden-breeze-releases/`).
- **Изоляция исходного ядра:** сюда попадают только материалы витрины (`docs/`, `README*.md`) и разрешённые артефакты в `Releases`. Исходный код ядра приложения, рабочие базы данных, внутренние адреса серверов, закрытые рабочие PR и секреты хранятся отдельно и сюда не копируются.
- **Архивы GitHub:** автоматически создаваемые GitHub архивы `Source code (zip / tar.gz)` содержат только файлы этой витрины и не включают исходный код приложения Golden Breeze.
- **Разделение каналов и контуров сборки:** пользовательские выпуски в этом репозитории относятся к каналу `stable` (первичная установка `FirstInstall`, контур `product`). Приёмочные сборки контура `acceptance` (включая внутренние тестовые сборки `internal`) выпускаются из той же ревизии исходного кода с отдельным ключом и манифестом стенда приёмки и не смешиваются с пользовательским каналом `stable`.
- **Актуализация витрины и согласованность материалов:** правила, периодичность и критерии обновления витрины (`README*.md`, `docs/{.,uk,en}/index.html`, `docs/{.,uk,en}/roadmap.md`, `docs/{.,uk,en}/first-start.md`) при выходе новых релизов и изменении статусов разработки зафиксированы в [Регламенте актуализации витрины (`docs/CONTENT-MAINTENANCE.md`)](docs/CONTENT-MAINTENANCE.md).

## 2. Формат пакета FirstInstall и происхождение выпуска

1. **Переход на `FirstInstall` без промежуточного bridge:**
   - Начиная с выпусков `v0.11.0-alpha` и `v0.12.0-alpha`, первичная установка на Windows x64 выполняется автономным пакетом `GoldenBreeze-FirstInstall-<версия>.exe`, а последующие обновления установленной программы доставляются напрямую через swap-воркер с собственного HTTPS-сервера обновлений. Старый промежуточный `GoldenBreeze-Setup-*.exe` больше не используется.
2. **Однозначное происхождение (`gb-distribution-provenance:v1`):**
   - Каждый выпуск в `Releases` однозначно связывает тег версии, `source_sha` исходного репозитория, имя установщика `FirstInstall`, его размер, `SHA-256` и `SHA-512`.
   - Разрешённый комплект артефактов релиза включает:
     - `GoldenBreeze-FirstInstall-<версия>.exe`
     - `GoldenBreeze-FirstInstall-<версия>.exe.sha256`
     - `build-manifest.json`
     - `first-install.json`
     - `first-install.json.sig` (подпись манифеста Ed25519)
3. **Ссылки на предварительные выпуски (`alpha` / `pre-release`):**
   - Поскольку текущие выпуски имеют статус `pre-release`, витрина и документация обязаны ссылаться на **конкретный проверенный тег и имя артефакта** (например, `/releases/tag/v0.14.0-alpha` и `/releases/download/v0.14.0-alpha/GoldenBreeze-FirstInstall-0.14.0-alpha.exe`) либо на общий список `/releases`. Использовать `/releases/latest` запрещено, так как GitHub исключает из него `pre-release`.

## 3. Подписи, HTTPS и отложенные платные реквизиты

Три уровня проверки решают разные задачи и не подменяют друг друга:

- **Сверка SHA-256 установщика:** позволяет пользователю убедиться, что скачанный файл `.exe` побайтово совпадает с доверенным опубликованным значением выпуска.
- **HTTPS-доставка обновлений (TLS) и подпись манифеста (Ed25519):** защищают канал доставки обновлений и подтверждают подлинность манифеста и пакетов обновления перед их применением программой.
- **Сертификат издателя Authenticode и отдельный домен — отложены по решению оператора:** исполняемый файл `.exe` не подписан платным сертификатом Windows Authenticode (его покупка и отдельный домен отложены до выхода продукта на прибыль и не являются блокерами выпуска). До приобретения Authenticode пользователи сверяют `SHA-256` и при первом запуске подтверждают установку в окне Windows SmartScreen вручную.

Никакие приватные ключи подписи, SSH-ключи, токены GitHub PAT, ключи провайдеров ИИ или служебные учётные данные не могут храниться в файлах этого репозитория.

## 4. Проверки доставки и граница приёмки

- **Доставка пользовательской сборки (`product` / `stable`):** перед публикацией выпуска для точных байтов `GoldenBreeze-FirstInstall-<версия>.exe` проверяются чистая установка `FirstInstall`, штатное удаление NSIS и обновление с предыдущего опубликованного выпуска с сохранением пользовательских данных и контролем завершения дочерних процессов.
- **Разделение контуров `product` и `acceptance`:** проверки, выполненные на выделенном стенде приёмки Windows x64 на приёмочной сборке (`acceptance`) той же ревизии кода (включая живую сессию `FTMO-Demo` и инъекцию неисправного тестового пакета для проверки аварийного отката к рабочей приёмочной сборке), явно отличаются в материалах витрины от проверок самого опубликованного установщика `stable`. Если межверсионный откат опубликованного `product`-установщика к предыдущему релизу отдельно не запускался, он не приписывается пользовательскому артефакту.
- **Разделение режимов торговой проверки (`dry-run` vs живые демо-сделки):** в публичных описаниях чётко разграничиваются расчётный проход обычной стратегии в Студии (сигнал, проверка ИИ, расчёт объёма и предпроверка ордера без отправки живого приказа в рынок) и реальные демо-сделки / серверный `trailing-stop`, выполненные через приёмочные и диагностические сценарии на `FTMO-Demo`.
- **Граница по реальным счетам (`Real`):** платформа поддерживает подключение как `Demo`, так и `Real` счетов MT5; блокировка реальных счетов действует исключительно в специальном тестовом диагностическом маршруте, а для обычной торговли честно фиксируется отсутствие заявленной завершённой приёмки на счёте `Real` без объявления всей платформы «закрытой для Real».
